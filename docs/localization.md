# English and Danish localization

English (`en`) is the default and fallback. The header has an English / Dansk selector;
the choice is remembered in `localStorage` as `knx-explorer-language`. Storage failures
are tolerated. The document language changes with the selection.

## Implemented

- i18next + react-i18next, with local resources under `src/locales/`; no translation service.
- Navigation, primary controls, static explanatory text, accessibility labels, Hop Count
  event messages, CAD names/descriptions, and common DPT editors have Danish translations.
- CAD search matches both English and Danish names and descriptions. Category values
  remain English identifiers internally, regardless of their displayed labels.
- Language changes rerender mounted components; they do not remount the app or reset
  telegrams, forms, selected pages, capture assignments, or simulation progress.
- Danish DPT numeric inputs accept decimal commas and normalize to decimal points before
  encoding. Mixed separators are not interpreted as thousands separators. Addresses,
  DPT IDs, canonical protocol names, raw bytes, and symbolic codes are not localized.

## Scope of this first release

This is a translated interface with English fallback, **not a completely translated
454-entry technical catalogue**. Imported DPT descriptions, many advanced codec field
names/validation messages, generated byte explanations, and some dynamic diagnostic
text remain English. The Danish interface explicitly states that reference text may
fall back to English. Existing unresolved standard interpretations remain unresolved;
localization does not change any codec or conversion rule.

Further work should translate those reference descriptions by DPT ID and migrate
remaining generated validation messages to structured presentation keys. Do not
translate canonical DPT standard names or infer protocol meaning from translated text.

## Maintaining resources

`en.json` and `da.json` have matching flat keys. `lookup.json` maps existing English UI
strings to stable keys for `tr(english)`, allowing gradual migration without translating
model data. The keys include a readable slug and a collision-resistant suffix. Keep a
key stable when editing its wording, and update its lookup entry if the call changes.
Missing lookup entries return the original English string.

For new dynamic messages, use semantic keys with `msg(key, {values})` and complete
sentences with `{{placeholders}}`, rather than concatenating translated fragments.
`routePresentation.ts` demonstrates translating model outcomes at the presentation
boundary. Components subscribe using `useTranslation()` even when they call `tr`.
Do not translate option values, model keys, CSS/data attributes, or user-entered names.

## Verification

`Localization.test.tsx` verifies matching resource keys/placeholders, remembered choice,
document language, unchanged generated bytes and source address, retained page and route
progress, Danish numeric input, mixed-separator rejection, English fallback, and Danish
CAD search/category identifiers. Run `npm test`, `npm run lint`, and `npm run build`.
